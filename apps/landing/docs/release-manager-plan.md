# Release Manager — audit and implementation plan

_Phase 0 output for the private Release Manager (brief phase 14), written after reading the real
repository: `apps/landing` (Vite SPA + Express API), `db/migrations`, `server/*`, `src/*`, `test/*`._

## 1. What the repository actually is

| Area | Reality in this repository |
| --- | --- |

## 2. Findings that shape the work

1. **There is no GitHub integration to reuse.** The Release Manager has to add one, server-side, with
   the least-privileged supported method (a fine-grained token with read-only access to the repository).
   It must degrade honestly when the token is absent: manual drafting stays usable.
2. **The public changelog is content, not data.** To give every release a permanent URL, canonical
   metadata and a social preview, releases need a stable slug and a body. The existing five entries
   are shipped history that can be verified in this repository, so they become the seed set — each
   with a slug and its own detail page — rather than being invented.
3. **The admin area is allowlist-based, not role-based.** "Authorized administrator" therefore means
   *allowlisted and email-verified*, which the existing `/api/admin` middleware already enforces on
   every route. The Release Manager mounts inside that router: no second authentication system, and
   no client-side-only hiding.
4. **Release Manager writes are customer-visible state.** The admin console footer currently says
   "Read-only, except settings and composed mail". Publishing a release changes what the public site
   says, so that sentence has to be corrected rather than left to lie.
5. **`X-Frame-Options: DENY` is set on `/api` responses** and `robots.txt` disallows `/admin`. Drafts
   therefore never leak through the public API, the sitemap, or social metadata — the public release
   endpoints only ever return rows in the `published` state.
6. **No build-time database access.** The sitemap and `llms.txt` are generated by the Vite plugin, so
   they can only list releases known at build time. Database-published releases are linked from the
   changelog index (crawlable) but cannot enter the static sitemap without a build-time database read.
   This is a known, documented limitation rather than a silent one.

## 3. Scope of this delivery

Delivered now:

- **Public changelog with permanent URLs** — index plus one detail page per release, with canonical
  URL, Open Graph and Twitter metadata, publication date, categories, full notes, shareable URL,
  mobile/desktop layout, and empty / loading / not-found / error states.
- **Private Release Manager** in `/admin/releases`: draft → review → approved → awaiting deployment →
  published, plus cancelled. Draft editing, preview, approval, publication, correction after
  publication (canonical URL preserved), audit trail, checklist, share composer.
- **GitHub linking** (pull request, commit, release, deployment) with server-side token auth, label
  classification (`release:feature`, `release:improvement`, `release:fix`, `release:security`), draft
  generation from real PR context, and a signed, idempotent webhook endpoint.
- **Deployment-aware publication**: a linked deployment must be observed as successful before an
  announcement can be published; a merged PR or a green build is never treated as a deployment.
- **Release checklist** with automatic checks (content prepared, deployment succeeded, approval
  recorded) and manually confirmed checks (tests, type check/lint/build, migrations, docs, claims,
  preview). Unknown checks are shown as unknown, never as passed.

Deliberately **not** in this delivery, and why:

- Phases 2–13 of the brief (the hosted-form developer platform, usage metering, developer billing,
  notification preferences, AEO content) are a separate product programme. They are not started here,
  and nothing in this delivery claims they exist.
- Automatic publication after a successful deployment is implemented but **disabled by default**
  (`RELEASE_AUTO_PUBLISH_AFTER_DEPLOYMENT`); it only ever acts on a release an administrator already
  approved.
- Social publishing is not implemented. The Release Manager produces copy and copies it to the
  clipboard; it never posts anywhere.

## 4. Data model

Migration `022_release_manager.sql` (additive, no data loss, reversible by dropping the four tables):

| Table | Purpose |
| --- | --- |
| `release` | The announcement: stable `slug`, title, summary, body, categories, status, release date, share text, approval and publication attribution. |
| `release_source` | One GitHub or manual reference per release: kind (`pull_request`, `commit`, `release`, `deployment`), provider, external id, URL, title, labels, observed state, observed deployment status. |
| `release_audit` | Append-only record of administrative actions: who did what, to which release, when. |
| `release_checklist_item` | Persisted per-release checklist answers for the manual checks. |
| `release_webhook_event` | Delivery ids of processed GitHub webhook deliveries, for idempotent retries. |

Constraints: slug unique and immutable once published; body/title/summary length-checked; status
constrained to the six known states; foreign keys to `"user"(id)` with `ON DELETE SET NULL` so
deleting an account never deletes release history.

Rollback: `DROP TABLE release_webhook_event, release_checklist_item, release_audit, release_source,
release;` — nothing outside the release feature reads these tables, and the public changelog falls
back to the bundled seed content.

## 6. Risks

| Risk | Mitigation |
| --- | --- |
| Publishing leaks a draft | The public endpoints filter on `status = 'published'`; drafts return 404, not 403, so unpublished slugs are not discoverable. |
| A webhook is delivered twice | `release_webhook_event` records the delivery id; a repeat is acknowledged and ignored. |
| A forged webhook publishes something | The `X-Hub-Signature-256` HMAC is verified against `GITHUB_WEBHOOK_SECRET` with a timing-safe compare before the body is parsed. Without a configured secret the endpoint refuses (503). |
| A merged PR is mistaken for a deployment | The deployment status comes from the GitHub Deployments API and is stored as `observed`; a release with a linked deployment only publishes when that observation is `success`. |
| The token leaks to the browser | The GitHub client is server-only; the browser only ever calls `/api/admin/releases/*`. No `VITE_`-prefixed variable is used for it. |
| An admin publishes a draft full of placeholders | The server refuses to publish while `TODO` markers remain, while the body is empty, or while a checklist item is unconfirmed. |
| The public changelog breaks when the API is down | The bundled seed content renders; the page says live releases could not be loaded instead of showing a confident, shorter list. |

## 8. Dependencies and blocked items

- `GITHUB_TOKEN` (fine-grained, read-only on the repository), `GITHUB_REPOSITORY`
  (`owner/repo`) and `GITHUB_WEBHOOK_SECRET` are **not set in this environment**. The feature ships
  working but honest: the admin screen says the GitHub integration is not configured and offers manual
  linking and manual drafting. No GitHub endpoint, token or event name was invented — the client uses
  the documented REST API (`/repos/{owner}/{repo}/pulls/{number}`, `/files`, `/deployments`,
  `/deployments/{id}/statuses`) and the documented `X-Hub-Signature-256` webhook scheme.
- Live billing, live email and destructive database operations are out of scope for this delivery and
  were not performed.
